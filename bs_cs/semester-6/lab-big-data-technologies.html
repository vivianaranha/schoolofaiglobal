Module 1

What makes data “big” and why scale changes design

Lab: Big Data Technologies uses what makes data “big” and why scale changes design as a building block for more advanced study. Start by understanding the plain-language purpose of the idea, the vocabulary attached to it, and the kinds of questions it helps us answer. In beginner-friendly terms, this module asks: what problem does this concept solve, and why would a computing professional care about it?

At a deeper level, we connect what makes data “big” and why scale changes design to the broader data and analytics pathway. We examine the assumptions behind the concept, how it interacts with adjacent topics in Semester 6: Data, Security, and Scalable Applications, and what changes when systems become larger, faster, more distributed, or more safety-critical. Strong students should look for trade-offs, limits, and edge cases rather than memorizing a single rule.

In practice, teams apply what makes data “big” and why scale changes design while building or improving a student information platform. The value of the topic becomes obvious when design choices need to be justified, tested, documented, and communicated to collaborators.

Aggregating Data with PySpark

PYTHON example with explanation and expected behavior.

from pyspark.sql import SparkSession

spark = SparkSession.builder.appName('sales-summary').getOrCreate()
df = spark.createDataFrame([
    ('North', 1200),
    ('North', 900),
    ('South', 1500)
], ['region', 'sales'])

summary = df.groupBy('region').sum('sales')
summary.show()

Why This Works

  • Create a Spark session to access the distributed processing engine.
  • Load or create a DataFrame with named columns rather than raw records only.
  • Use groupBy and aggregation to summarize large data logically.
  • Treat the same pattern as a building block for much larger datasets.

Expected Output

Displays total sales per region using distributed-style DataFrame operations.

Orchestrating a Data Pipeline with a DAG

PYTHON example with explanation and expected behavior.

from airflow import DAG
from airflow.operators.empty import EmptyOperator
from datetime import datetime

with DAG('daily_pipeline', start_date=datetime(2024, 1, 1), schedule='@daily', catchup=False) as dag:
    extract = EmptyOperator(task_id='extract')
    transform = EmptyOperator(task_id='transform')
    load = EmptyOperator(task_id='load')

    extract >> transform >> load

Why This Works

  • Express the workflow as a graph so dependencies are visible and schedulable.
  • Give each task one stage-oriented responsibility such as extract, transform, or load.
  • Declare a schedule to automate repetitive pipeline execution.
  • Use dependency arrows to make the order of work unambiguous.

Expected Output

Defines a daily three-stage pipeline with explicit task ordering.
